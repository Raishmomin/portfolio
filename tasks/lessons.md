# Lessons

- Never `pkill -f "<pattern>"` when the pattern also appears in the running shell's own command line — it kills the shell, not the target. Kill servers by port PID (`lsof -ti tcp:<port>`), then confirm the port is free before starting a new server.
- After restarting a server for a comparison, confirm the NEW process is the one listening (check its log for "Ready" and that asset URLs return 200) before trusting any metric. A suspicious jump (perf 55 -> 100) means verify, not celebrate.
- Don't benchmark (Lighthouse/CWV) while background browser jobs are running; check `uptime` load first and A/B both builds back-to-back on an idle machine.
- In chrome-headless-shell, `--use-gl=swiftshader` DISABLES WebGL instead of enabling it (caught by the scout). For screenshotting 3D pages use the default GL or `--use-angle=swiftshader --enable-unsafe-swiftshader`, and assert `getContext('webgl2')` succeeds before trusting a blank capture.
- `lsof -ti tcp:<port>` can miss processes started by other agents/sandboxes; fall back to `ss -ltnp | grep :<port>` for the PID before assuming a port is free.
- tsconfig alias `@/*` maps to `app/*` only — `@/components/...` does NOT resolve. Import components by relative path (or add an alias deliberately, repo-wide).
- /tmp (scratchpad) is wiped on reboot. Anything a later phase depends on (rulebooks, checkers, specs) must live in the repo (tasks/), and every agent's work must be committed to a branch before the session can end. Commits in git worktrees survive because they live in the main repo's .git.
- Test capability gates on the OWNER's real hardware before calling a feature done. If verifiers must spoof navigator.hardwareConcurrency to see a feature, the gate is too strict for real users (a 4-thread laptop lost the whole 3D experience). Gate only genuinely weak devices and rely on a runtime frame monitor.
- Respect prefers-reduced-motion by default, but give visitors an explicit opt-in that overrides it, and make toggles show the EFFECTIVE state (a toggle that looks "on" while nothing animates reads as broken).
- (Owner correction, 2026-11-06) A clever metaphor is not a portfolio visual. The "Kubernetes pods" cluster was abstract and not visibly tied to sections, so a normal visitor couldn't read it. Rule: every 3D visual must be understandable in 3 seconds without explanation, show the section's actual subject (skills as a skill network, career as a timeline, AI projects as AI pipelines), and carry a one-line plain-language caption in the DOM. Before building, describe each section's visual in one sentence a non-developer would understand; if you can't, redesign it.
- "Fully animated" was the owner's goal; restrained motion read as "static". Match the motion level to what the owner asked for, while keeping accessibility opt-outs and SEO guardrails.
- `failIfMajorPerformanceCaveat` does NOT reject SwiftShader in headless-new Chrome (Lighthouse / PageSpeed Insights). Always also check WEBGL_debug_renderer_info for software renderers (swiftshader|llvmpipe|basic render), or lab TBT explodes (6.6 s measured).
- Run Lighthouse on the integrated build after every relaxation of a capability gate — loosening the gate for real users can silently let lab/CI browsers in.
- (Owner correction, 2026-11-06) Verifying each scene in isolation is not verifying the design. I shipped 10 sections with one identical composition (panel left, 3D right): the stale Work scene bled through the services/writing/FAQ panels, and subpages had no stage at all. To the owner it read as "animation on one side, design doesn't match". Rule: before calling a visual phase done, scroll the WHOLE site in Playwright (every section of home, every page, desktop and mobile; video or frame strip) and judge it as a visitor would. Check that compositions vary section to section, that the content itself moves (cards, not just the background), that no visual from a previous section lingers where it doesn't belong, and that subpages share the home page's design language.
- (Owner correction, 2026-11-06) Do not put self-promotional question CTAs ("Want a 3D site like this one?") on the owner's portfolio without asking; state services plainly instead.
- (Owner correction, 2026-11-06) A 3D visual that sits behind opaque content cards is invisible to the visitor, even when it is "framed" correctly. Check at the owner's real viewport (1920×915 here, not only 1440×900) that each scene's key elements (milestones, nodes) land in visible space and line up with the DOM they illustrate.
- (Owner correction, 2026-11-06) If one group of items gets a per-item 3D treatment (the AI projects' pipelines), every item of that kind expects one (all projects, driven by each project's tech stack). Don't leave the rest generic.
- (2026-11-07) A reboot wiped /tmp again mid-phase and took 3 lane worktrees with uncommitted agent work, the QA tools and the research notes. Rule: lane worktrees and tools live in /home/raish/raish/.my-app-lanes/ (persistent, outside the repo); QA scripts and research notes are committed under tasks/qa and tasks/research; lane agents commit a WIP checkpoint at least every ~15 minutes.
- (Owner correction, 2026-11-07) A scene that is technically correct but SPARSE (a thin wavy line with small dots in a narrow strip with empty space around it) reads as decoration, not as the subject. Every section's scene should fill its free area with recognisable objects for what the section is about, react to what the visitor does in that section, and be checked at the owner's real viewport (1536x732 @1.25) by someone other than its builder before it ships. Sections left on the generic ambient field (services, FAQ) read as "no animation".
- (2026-11-08) A network outage (EAI_AGAIN) killed 9 workflow agents mid-task overnight, and the workflows treated a dead agent as "done", so lanes silently skipped their fix and review rounds. Rule: wrap every workflow agent() in a retry (2 retries, with a "resume from the worktree state" note). Keep each lane's open issues in a file on disk (data/fm3/open/<lane>.md), so a restart never depends on journals. After any outage or reboot, check each lane's git status and commit interrupted work as an explicit WIP before restarting agents.
- (2026-11-08) The workflow harness relays the user's LATEST message to every agent a workflow starts, with "this request wins" priority. The owner asked "how much time?" while I was launching the finishing workflows, so 6 agents returned time estimates and changed nothing (about 30 minutes lost). Rule: start long workflows only when the user's latest message asks for the work itself. Otherwise start standalone background agents whose only context is a brief file. Begin every agent brief with "do the work; never stop to answer time or status questions; the lead talks to the owner". Within ~5 minutes of launch, check that each agent is editing files rather than replying in prose.
